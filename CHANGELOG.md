## [Unreleased]

### Fixed
- `docker-compose.yml` did not parse (`mapping key "smartkin-frontend" already defined`): commit `287d4fc` added back the old `smartkin-frontend` block, the one with inline settings and a required `SMARTKIN_FRONTEND_VAULT_PATH`. Only the block that reads `../smartkin-frontend/local.env` stays. That commit also published the backend on host port 443, the port the frontend and nginx already use. As a result, on a machine running nginx, `host-gateway:443` (Vault, Config Server) never reached it. The backend is published on `8166:8166` again.

### Changed
- The Feign base URLs are now overridden with `BACKBONE_BASE_URL` and `MERCURY_BASE_URL` (they were `BACKBONE_URL` and `MERCURY_URL`); the QA defaults stay. Fixes after commit `287d4fc`, which left 4 tests failing: `umdc.backbone.base-url` points again at `umdc.clients.backbone.url` (it read `${BACKBONE_BASE_URL}` with no default, so it did not resolve without that variable), and `BOOTSTRAP_SERVER_PORT` is optional again (`${BOOTSTRAP_SERVER_PORT:}`; without it the literal placeholder ended up in `bootstrap.servers` and the Kafka consumer did not start). `FeignClientUrlConfigTest`, the user guide, the technical guide and the QA runbook use the new names.
- **Breaking for operators.** The service's own properties moved from the `prx.*` prefix to `umdc.*`, the prefix the `com.umdc` libraries already use, and the Kafka variables of `application.yml` were renamed from `KAFKA_*` to `BOOTSTRAP_*` (the names of the Vault keys): `umdc.bootstrap.server.*`, `umdc.producer.mercury.topic`, `umdc.verification.code.template.id`, `umdc.smartkin.*`, `umdc.clients.*`, `umdc.security.revocation.*`, `umdc.cache.lesson-catalog.*`, `umdc.kafka.consumer.*`, `.security.*` and `.topics.*`, `umdc.interaction-events.retention`, `umdc.logging.trace.enabled` (now one key shared with the libraries), and `BOOTSTRAP_SECURITY_PROTOCOL`, `BOOTSTRAP_SASL_*`, `BOOTSTRAP_SSL_*`, `BOOTSTRAP_CONSUMER_*`, `BOOTSTRAP_ERROR_TOPIC`. The source (`@Value`, `@ConfigurationProperties`, `@ConditionalOnProperty`), the tests, `config/native.env` (`PRX_*` became `UMDC_*`), `scripts/kafka-create-topics.sh` and the documentation follow the new names; `application.yml` also had one reference left to `prx.clients.backbone.url`, now `umdc.clients.backbone.url`. A Config Server or Vault entry that still uses the old names is silently ignored and the default applies, so the file `smartkin-backend-remote-supabase.yml` of stage-folder-config was updated in step (its `prx:` block is now under `umdc:`, with `revocation` under `umdc.security`). Verified by starting the service with the new `application.yml` and that file imported above it: with Redis stopped a valid session token answers 503 (revocation forced on by the Config Server, fail closed), with Redis up it reaches the repository. Full suite: 484 tests, PMD/CPD/JaCoCo pass. The technical guide has the old-to-new table.
- S-5 closed: after the smartkin-frontend upgrade chain (PRs #7 to #24) was merged, Dependabot reports 0 open alerts in smartkin-frontend (23 `fixed`, none dismissed) and in smartkin-backend. `docs/SECURITY_REVIEW_MVP.md` and `docs/BACKLOG_MVP.md` updated; the frontend merge state of S-2, X-6 and FE-4 to FE-14 in the backlog is now "merged".
- Authentication: `SmartKinBackendApplication` no longer scans the security library's `SecurityConfig` (the decommissioned Keycloak-style resource-server chain, excluded the same way by mercury and zerobound-rest). The new `SessionTokenSecurityConfig` (it replaces `HealthProbeSecurityConfig`) lets `/api/v1/**`, the health probes, `/error` and Swagger through the filter chain and denies the rest; the library's `SessionJwtInterceptor` authenticates the API with the `session-token` header through `SessionJwtServiceImpl` (signature, expiry, type, revocation). Before, a valid `session-token` answered 401 because the removed chain asked for a bearer token. Verified on the JVM jar: a valid token reaches the repository; wrong key, `alg: none`, expired and no token answer 401; health `UP`; `/actuator/env` 403. The `spring.security.oauth2.*` and `umdc.security.keystore/truststore` properties and the OAuth2 resource-server autoconfiguration are removed. This is the local half of security finding S-1; the check against the real environment stays in QA.
- GraalVM: the native binary now builds and starts (`Started in 0.457 seconds`, 144 MiB, liveness `UP`, same session-token behaviour as the JVM jar) when the keystores are mounted and `SSL_KEYSTORE_URL`/`SSL_TRUSTSTORE_URL` point at them. Verified with `NATIVE_QUICK_BUILD=true` and a throwaway PostgreSQL, without Vault, the Config Server, Redis or Kafka; the JVM image stays the one to deploy until it is checked against the real environment.
- New optional `SSL_KEYSTORE_URL` and `SSL_TRUSTSTORE_URL` (with a scheme, e.g. `file:/...`) override the classpath keystore names for the TLS bundle, Vault, the Config Server and Eureka, so the GraalVM binary, which does not embed the `.jks` files, can read them from a mounted path. The JVM jar keeps using the classpath. Tests: `SessionTokenSecurityConfigTest`, `SmartKinBackendApplicationScanTest`, `SslLocationPropertiesTest`.
- Configuration moved from `bootstrap.yml` to `application.yml` with `spring.config.import: "optional:vault://,optional:configserver:"`, the same solution as zerobound-rest and backbone-rest. `spring-cloud-starter-bootstrap` is removed (its nested bootstrap context was what Spring AOT captured instead of the real application, so the GraalVM binary stopped with `no ServletWebServerFactory bean`). The `spring.cloud.vault.*` and `spring.cloud.config.*` properties are the same; new optional variables `VAULT_KV_BACKEND` (default `UMDC`) and `VAULT_KV_CONTEXT` (default the application name); `CNFS_URI`, `SPRING_CLOUD_CONFIG_LABEL` and `SPRING_BOOT_PROFILE_ACTIVE` gain defaults; `SPRING_BOOT_CLOUD_BOOTSTRAP_ENABLED` and `spring.cloud.config.port` are gone; Vault and the Config Server now trust the PRX internal CA through `classpath:${SSL_TRUSTSTORE_LOCATION}`. `config/local.env`, `config/native.env`, the tests and the docs are aligned. Verified: the JVM jar starts (`Started in 7 s`, liveness UP, `/api/v1/**` 401 without a token) and 442 tests pass.
- `NativeRuntimeHints` registers the properties types bound during the config import (`VaultProperties`, `VaultKeyValueBackendProperties`, `ConfigClientProperties`, `RetryProperties`, `TlsProperties` and nested classes), the `UUID[]`, `Long[]`, `Integer[]` and `String[]` arrays Hibernate instantiates by reflection, and the `HttpServletResponse`, `HttpSession` and `WebRequest` proxies. `Dockerfile.native` builds and the binary now goes past the configuration import, Hibernate and Tomcat; it still stops because the `*.jks` keystores are not embedded in the binary, so it stays experimental (details in the technical guide).
- Dependencies, keeping Spring Boot 4.1.1, Spring Cloud 2025.1.3 and Java 25: PostgreSQL JDBC 42.7.14, springdoc 3.2.0, Surefire 3.6.0, ASM 9.11.1, Gson 2.14.0, and security overrides shared with zerobound-rest for transitive dependencies (Tomcat 11.0.26, Jackson 2.21.7 / 3.1.7, Logback 1.6.3, Netty 4.2.18, Nimbus JOSE 10.10, httpclient 4.5.14, Bouncy Castle 1.86). The `com.umdc` libraries stay at 0.0.3, the latest release in the repository.
- S-2 (security): a parent can no longer link an arbitrary user as a child. `POST /api/v1/children` (`linkChild`) and `ChildRequest` are removed from the API and the contract (now 29 operations); a user joins a family only by accepting an invitation, or because the parent created that user's account. `ChildServiceImpl` loses `link` and its `BackboneClient` and `ParentRepository` dependencies. This also removes the "does not exist" / "already linked" difference that let a parent probe user ids (S-9).

### Added
- QA runbook, technical guide and user guide: how SmartKin's verification e-mail is set up in mercury (mercury PR #52: templates `sk_verification_{es,en}.ftl` and `scripts/smartkin/seed-templates.sql`). Section 3 of `docs/QA_RUNBOOK_MVP.md` gets a "The verification e-mail (mercury)" procedure in five steps (deploy mercury with the templates, register them in its database, set `PRX_VERIFICATION_CODE_TEMPLATE_ID` to the `template_defined_id` of `sk_verification_es.ftl`, point `MERCURY_EMAIL_TOPIC` at `mercury-email-messages`, check with a registration), a diagnosis of the three failures (mercury discards an incomplete message, the template is missing from the image, the template is not of the verification-code type so the confirmation answers 404), a row in the Vault table and a "done when" item. The technical guide has a Mermaid flow and warns that `umdc.verification.code.template.id` is the template_defined id in SmartKin and the template TYPE id in mercury. The runbook also stops pointing at the removed `bootstrap.yml`.
- Kafka security settings for the producer and the consumer (`KafkaSecurityProperties`, `prx.kafka.security.*`). Until now both set only `bootstrap.servers`, so a cluster that requires TLS, such as Aiven, could not be reached and the events of the MVP (points, achievements, notifications) and the verification e-mail sent through mercury would have failed. The settings become Kafka client properties of both factories: `SSL` (client certificate) and `SASL_SSL` (SCRAM user and password) with a PEM, `PKCS12` or `JKS` truststore and keystore, the client certificate and key as the two files Aiven delivers (read and handed to the client as PEM text), the host name check and the JAAS line. The default `PLAINTEXT` adds nothing, so local brokers and the existing tests behave as before. The environment variables are the ones mercury uses (`KAFKA_SECURITY_PROTOCOL`, `KAFKA_SSL_*`, `KAFKA_SASL_*`). Files come from the file system, never the classpath (a GraalVM binary does not embed them); an unreadable file stops the start with its path and never its content, an unknown protocol is rejected with the valid ones, and `toString()` hides passwords and the JAAS line. Verified against a real Aiven service, read-only: an `AdminClient` built from these properties connected over TLS and listed the four SmartKin topics. 15 new tests (`KafkaSecurityPropertiesTest`, `KafkaProducerConfigTest`, one consumer case). `KafkaProducerConfig.kafkaTemplate` now receives the producer factory as a parameter. Technical guide (with a Mermaid flow), user guide and QA runbook updated.
- `docs/db/smartkin_roles_sql_editor.sql`: the database-roles script for clients that are not psql. `smartkin_roles.sql` uses psql meta-commands (`\if`, `\set`, `\gexec`, `-v`), so run from DataGrip (or DBeaver, pgAdmin, the Supabase SQL editor) it executed only its first guard and answered "owner_password is required". The new file is a single `do` block with no meta-commands and the same result: two login roles without superuser, `CREATEROLE`, `CREATEDB` or `BYPASSRLS`, the schema handed to `smartkin_owner`, objects created by another role moved to it, DML-only grants for `smartkin_app`, idempotent and password-rotating. The operator edits the two passwords and the expected database at its top; it stops while they are `CHANGE_ME_*` or in the wrong database. The psql version now says at the top that it needs psql, and its error points to the editor version. `DatabaseRolesScriptContainerTest` runs the editor version over JDBC (roles, migrations as the owner, DML yes and DDL no for the application role, hand-over of existing tables, password rotation, placeholder and wrong-database stops) and checks the psql version's message. QA runbook, user and technical guides updated.
- `scripts/db-migrate.sh` creates the tables: it runs the Flyway migrations (V1 to V6) with the Flyway command-line image `flyway/flyway:12.4.0`, the version Spring Boot 4.1.1 brings, as the schema owner `smartkin_owner`, so the service later finds nothing pending. `info` (default) changes nothing, `validate` checks the applied migrations, `migrate` applies them. It refuses the Supabase pooler port (6543) and the `postgres` user, and the password reaches the container through the environment, not a command line. Verified on PostgreSQL 17: 14 tables and 4 enums, owned by `smartkin_owner`; a second run is a no-op; the service starts with Flyway enabled and validates the history the script left.
- `scripts/kafka-create-topics.sh` creates and verifies the four Kafka topics (`smartkin.activity.assigned.v1`, `smartkin.quiz.completed.v1`, `smartkin.achievement.earned.v1`, `smartkin.events.error.v1`; same names and overrides as the service) with `--if-not-exists`, 3 partitions and replication factor 3 by default, an optional `KAFKA_CLIENT_PROPERTIES` for SASL/SSL, `--dry-run`, and a non-zero exit when a topic is missing or has fewer partitions than expected. Verified on Apache Kafka 4.2.0. The QA runbook (steps 1 and 2), the technical guide (with a Mermaid flow), the user guide and the backlog (BE-3) point to both scripts. Running them against Supabase and the real brokers still needs the credentials from Vault.
- `docs/db/smartkin_roles.sql`: one idempotent psql script that creates the two database users the changes require and wires them together. `smartkin_owner` owns the `smartkin` schema and runs Flyway (`SMARTKIN_FLYWAY_USERNAME` / `_PASSWORD`); `smartkin_app` is what the service connects as (`SMARTKIN_DB_USERNAME` / `_PASSWORD`) with only `SELECT`/`INSERT`/`UPDATE`/`DELETE` on the tables and `USAGE`/`SELECT` on the sequences (also for tables added by later migrations, through default privileges). Neither role is a superuser or can create roles or databases, or bypass Row Level Security. The passwords are psql variables (`-v owner_password=... -v app_password=...`), `-v expected_database=umdevc` refuses to run in another database, running it again rotates the passwords, and an environment whose tables were created by another role (for example `postgres`) gets its tables, sequences and enum types handed to `smartkin_owner`. `DatabaseRolesScriptContainerTest` runs it with real psql on PostgreSQL 17. QA runbook step 1, the technical and user guides, the D-3 decision and the schema bootstrap script point to it; the manual `alter role smartkin_app ... login` step is gone.
- QA support for the steps that cannot be done from the repository (BE-2, BE-3, X-1, X-4, S-1). `docs/QA_RUNBOOK_MVP.md`: ordered steps (database and `smartkin_app`, Kafka topics with commands, the Vault keys, start, Flyway V1 to V6, smoke test, registration to login through the BFF, end to end, metrics) with how to tell each one worked and a "done when" checklist. `scripts/qa-smoke.sh` (needs `curl` and `jq`): the S-1 check (a tampered signature, an unsigned `alg: none` token, another user's payload and, if given, expired and revoked tokens must all answer 401 on four endpoints), the invitation flow (single use, wrong code 404, parent cannot accept) and the vertical slice, exiting non-zero on any failure; verified here against a local stand-in service, once secure and once not verifying tokens.
- BE-14 alert rules. `docs/ops/smartkin-events.rules.yml` (Prometheus): `SmartKinEventDeadLettered` (warning), `SmartKinDeadLetterFailed` (critical, the error topic itself cannot be written) and `SmartKinEventRetriesHigh` (warning), plus the log lines to alert on while there is no metrics registry. `AlertRulesTest` parses the file and checks every metric it queries is still registered by `ErrorTopicMonitor`. Exposing a Prometheus registry stays with the platform team (the runbook says what to add and why it needs protecting).
- Achievement catalog for the product team. `docs/ACHIEVEMENTS_CATALOG.md` explains the three rule types and their limits; `docs/db/achievements_catalog_proposal.sql` proposes eight achievements (an idempotent upsert that also replaces the three V5 placeholders), not applied by any migration. `AchievementCatalogProposalTest` keeps every rule valid and the ids unique.
- `docs/BACKLOG_MVP.md`: execution status brought up to date (BE-4 to BE-14 merged, FE-4 to FE-15, S-2, S-5, X-5, X-6 and what is still blocked on QA or people).

- Child invitations. `POST /api/v1/children/invitations` (`createChildInvitation`) creates a one-time code (`ABCD-EFGH`, 8 characters from an alphabet without look-alikes, valid 7 days, at most 10 pending per parent); the code is returned once and only its SHA-256 is stored. `GET /children/invitations` (`listChildInvitations`) lists them with `PENDING`, `ACCEPTED`, `REVOKED` or `EXPIRED` and never shows the code; `DELETE /children/invitations/{invitationId}` (`revokeChildInvitation`) revokes a pending one; `POST /children/invitations/accept` (`acceptChildInvitation`) lets any signed-in user without a parent or child profile become the parent's child with the grade and avatar of the invitation. An unknown, malformed, used, revoked or expired code answers the same 404, so codes cannot be probed; a user who already has a profile gets 409. The code is claimed with one conditional update and the child is created in the same transaction, so two users cannot use one code and a failed accept leaves the code usable. Migration `V6__child_invitations.sql` (table `child_invitation` with RLS and a policy for `smartkin_app`), `ChildInvitationEntity`, `InvitationStatus`, `ChildInvitationRepository`, `InvitationCode`, `ChildInvitationService` / `ChildInvitationServiceImpl` and `ChildLinker`, the single place that creates a child profile.
- Child account creation. `POST /api/v1/children/accounts` (`createChildAccount`): a parent creates the child's user (first and last name, birth date, e-mail, password, optional grade and avatar) and links it in one call. It reuses `UserService.create` (alias generation, backbone user, verification e-mail), requires the child to be under 18, falls back to the parent's phone number, relays the e-mail conflict as 409 and, if the profile cannot be saved, deletes the new user again so no orphan account remains. Returns the child, the alias to sign in with and the e-mail. `ChildAccountService` / `ChildAccountServiceImpl`.

### Added
- `Dockerfile.native`: faster and more traceable image build, aligned with zerobound-rest. GraalVM and Maven are downloaded in their own stages, so BuildKit fetches them in parallel and a version bump of one does not invalidate the other; the builder no longer installs `curl`; Maven runs with `-ntp` and `-Dmaven.artifact.threads=8`; the Maven cache mount is `sharing=shared` so two builds no longer queue on a lock; the runtime copies use `COPY --link --chown --chmod` (no extra `chown -R` layer). The runtime stage gains `BUILD_COMMIT`, `BUILD_BRANCH` and `BUILD_TIME` (environment and OCI labels). The image is still experimental (the binary does not start yet).
- X-5: `docs/SECURITY_REVIEW_MVP.md`, the security review of the MVP across both repositories (9 findings with severity and status, what was verified and what was not covered). Open items: S-1 verify in QA that the PRX library rejects forged, unsigned, expired and revoked tokens, since the controllers read the `uid` from the token payload without checking the signature; S-2 `POST /children` links any existing user without that user's consent; S-4 rotate the Vault token in the frontend history. Fixed in smartkin-frontend: secrets in the BFF logs.
- BE-13: `EndToEndFlowContainerTest`, the full MVP slice on real PostgreSQL (Flyway V1 to V5), MongoDB and Kafka with the production services, publisher, consumers and achievement evaluator: link a child, browse the catalog, assign an activity (notification through Kafka), report progress, fail and then pass the server-graded quiz, and receive the quiz points, the achievement, its points and its notification asynchronously; assigning again after completion, 404 for another family, and no event in the error topic. It does not start the web layer, the security library, Vault, TLS or Redis (needs the QA environment of BE-2).
- BE-14: error topic monitoring. `ErrorTopicMonitor` wraps the consumer error handling and records `smartkin.events.delivery_failed` (per failed attempt), `smartkin.events.dead_lettered` (records sent to the error topic, tagged by topic and cause) and `smartkin.events.dead_letter_failed` (the error topic itself could not be written; the error propagates so the offset is not committed), plus `ERROR` logs starting with `DEAD_LETTERED` / `DEAD_LETTER_FAILED`. Retry and dead-letter behavior is unchanged. `KafkaConsumerConfig.smartKinErrorHandler` now receives a `MeterRegistry`. The alert rule and a metrics endpoint/registry remain with the platform team.
- BE-12: notification inbox API. `GET /api/v1/notifications[?unread=&page=&size=]`, `GET /api/v1/notifications/unread-count`, `POST /api/v1/notifications/{notificationId}/read` and `POST /api/v1/notifications/read-all` (`listNotifications`, `getUnreadNotificationCount`, `markNotificationRead`, `markAllNotificationsRead`). Every user reaches only their own notifications (the `uid` of the token is the `user_id`); another user's notification answers 404; marking as read is idempotent and keeps the first `readAt`; mark-all is a single `update` limited to the caller. New `NotificationMapper`, `UnreadCountResponse` and repository methods `findByUserId`, `findByUserIdAndIsReadFalse`, `countByUserIdAndIsReadFalse`, `findByIdAndUserId` and `markAllRead`. All 25 operations of the MVP contract are now implemented.
- BE-11: achievement rules. Achievements are earned by a JSON rule in `achievements.requirements` with three types: `QUIZZES_PASSED` (distinct lessons passed), `ACTIVITIES_COMPLETED` (distinct activities completed) and `POINTS_REACHED` (point balance), each with a `threshold`. `AchievementEvaluator` (own `REQUIRES_NEW` transaction) awards each achievement once per child with `insert ... on conflict do nothing` and publishes `ACHIEVEMENT_EARNED` after the commit; `AchievementTrigger` runs it after a passed `QUIZ_COMPLETED` and after `ACHIEVEMENT_EARNED` (once the points are booked, so `POINTS_REACHED` and cascades work) and after a child completes an activity by reporting 100, never failing the caller. Invalid rules are logged and skipped. Migration `V5__achievement_rules.sql` adds the unique index on `child_achievements (child_id, achievement_id)` and seeds three placeholder achievements. `SmartKinEventListener` and `ProgressServiceImpl` now receive an `AchievementTrigger`; `DomainEventDispatcher` also publishes `ACHIEVEMENT_EARNED` and exposes `afterCommit`.
- BE-10: points and achievements API. `GET /api/v1/children/{childId}/points[?page=&size=]` and `GET /api/v1/children/{childId}/achievements` (`getChildPoints`, `listChildAchievements`). Readable by the child and by the linked parent (another family's child answers 404, a sibling 403); read-only, since points and achievements are written by the event consumers. Points come as the balance plus a page of movements, newest first; achievements newest first with the achievement data loaded in one query. New `RewardsMapper` and repository methods `PointRepository.findByChildId` and `ChildAchievementRepository.findByChildIdOrderByEarnedAtDesc`.
- BE-9: quiz attempts API. `POST /api/v1/assignments/{assignmentId}/quiz-attempts` and `GET .../quiz-attempts` (`submitQuizAttempt`, `listQuizAttempts`). The server grades the answers with `QuizGrader` (a question is correct only for the exact set of correct options, no partial credit; percentage rounded down; passed at `passingPercentage`), stores the attempt in MongoDB with the lesson version, keeps the best score in the progress, completes the assignment when the quiz is passed and publishes `QUIZ_COMPLETED` after the commit. Only the assigned child may submit; `maxAttempts` per assignment answers 409; unknown questions or options answer 400. The attempt is inserted first and deleted again if the progress cannot be written. New `ProgressRecorder`, `QuizAttemptMapper` and repository methods `countByAssignmentId` / `findByAssignmentIdOrderByAttemptNumber`.
- `DomainEventDispatcher`: the publish-after-commit logic of `ACTIVITY_ASSIGNED` (BE-7) moved to a shared component (also used by `QUIZ_COMPLETED`); behavior unchanged.
- BE-8: progress API. `GET/PUT /api/v1/assignments/{assignmentId}/progress` and `PUT /api/v1/assignments/{assignmentId}/feedback` (`getProgress`, `updateProgress`, `putParentFeedback`). Only the assigned child reports progress (first report sets `startTime`, the percentage never goes down, 100 sets `completionTime` once and frees the activity to be assigned again); only the assigning parent leaves feedback; before the child starts, progress reads as 0%. Updates lock the assignment (`findForUpdateById`, `PESSIMISTIC_WRITE`) so concurrent first reports cannot violate the unique key of `activity_progress`. Anyone who cannot reach the child gets 404.
- BE-7: assignments API. `POST /api/v1/assignments`, `GET /api/v1/assignments[?childId=&page=&size=]` and `GET /api/v1/assignments/{assignmentId}` (`assignActivity`, `listAssignments`, `getAssignment`). A parent assigns an active activity only to their own children (optional future `dueDate`; 409 while the child has the same activity open); parents list all their children's assignments, children their own, newest first and paged; other families' assignments answer 404. `ACTIVITY_ASSIGNED` is published after the database commit and never blocks or fails the assignment. New `ClockConfig` (`Clock` bean), generic `PageResponse<T>`, `AssignmentMapper` and repository methods `findByChildId`, `findByChildParentId`, `existsOpenAssignment` and progress lookups.
- BE-6: catalog API. `GET /api/v1/topics`, `/topics/{topicId}/lessons`, `/lessons/{lessonId}`, `/activities[?topicId=]` and `/activities/{activityId}` (`listTopics`, `listTopicLessons`, `getLesson`, `listActivities`, `getActivity`). Topic lessons use the Redis-cached `LessonCatalogService`; only `PUBLISHED` lessons and `is_active` activities are served (404 otherwise). The lesson response types have no `correct` flag on options and no question feedback, so answers cannot leak. Migration `V4__activity_lesson_link.sql` adds the nullable `smartkin.activities.lesson_id` (plain id, no foreign key; existing activities keep a `null` lesson) and `ActivityEntity.lessonId`.
- BE-5: ownership rules in one place. `AccessPolicy` (`security.access`) decides who may reach which child (`viewChild`: the child or the linked parent; `manageChild`: only the linked parent) and returns `OWNER`, `SELF`, `NOT_VISIBLE` (404, hides other families' ids) or `FORBIDDEN` (403) together with the loaded child. `ChildServiceImpl` and `ParentServiceImpl` use it with no change in their answers; later endpoints (assignments, progress, quiz, points) will too. Tests: `AccessPolicyTest` and `CrossFamilyAccessContainerTest` (two families on PostgreSQL).
- BE-4: parent and child profiles. `GET/PUT /api/v1/parents/me` and `GET/POST /api/v1/children`, `GET/PUT /api/v1/children/{childId}` (operations `getMyParentProfile`, `putMyParentProfile`, `listMyChildren`, `linkChild`, `getChild`, `updateChild` of the contract). The caller is the `uid` of the session token: a user with a `parent` row is a parent, one with a `child` row a child. A parent reaches only their own children; a child of another family answers 404. Linking checks that the user exists in backbone, is not the caller and has no parent or child profile yet (409 otherwise, also on a concurrent link). New `ParentService`/`ChildService`, `ParentMapper`/`ChildMapper` and `ChildRepository.findAllByParentId`. `ControllerContractConformanceTest` compares every implemented controller with `docs/api/openapi-v1.yaml`.
- X-2: MVP API contract `docs/api/openapi-v1.yaml` (OpenAPI 3.0.3, 25 operations: parents and children, catalog, assignments and progress, quiz attempts, points and achievements, notifications) and decision record `docs/decisions/D-6-mvp-api-contract.md`. It is documentation only: no controller or behavior changes. `OpenApiContractTest` keeps it well formed (resolved references, unique operation ids, no `correct` flag on quiz options, existing user endpoints not redefined).
- `docs/BACKLOG_MVP.md`: analysis of smartkin-backend and smartkin-frontend and the unified MVP backlog (tickets BE-n, FE-n and X-n) with the execution status of each ticket.

### Added

### Fixed
- `docs/db/smartkin_roles_sql_editor.sql` asked the operator to edit the two passwords in the repository file. Doing so left real passwords in a versioned file, made `mvn test` fail in five places (`DatabaseRolesScriptContainerTest`: the tests look for the `CHANGE_ME` placeholders to put their own passwords, so the script ran with the real ones and the tests could not log in, and the placeholder check hit the database check instead) and risked committing the secrets. The instructions now say to copy the file (`~/smartkin_roles.local.sql`; `*.local.sql` is git-ignored), edit the copy and delete it afterwards, in the script header, the QA runbook and the user and technical guides. New `RolesScriptsHygieneTest` (no Docker) fails with a clear message and the restore command (`git checkout -- ...`) when the file has no placeholders or any `docs/db/*.sql` holds a literal password, so it also stops a pull request that carries one; the container tests assert the placeholders before substituting them, so a dirty file explains itself instead of failing in five ways.
- `docs/db/smartkin_roles.sql` and `docs/db/smartkin_roles_sql_editor.sql` failed on Supabase with `permission denied to alter role: Only roles with the SUPERUSER attribute may change the SUPERUSER attribute`. A role that is not a superuser (Supabase's `postgres`) may not even name `NOSUPERUSER`, `NOREPLICATION` or `NOBYPASSRLS` in `ALTER ROLE`, and both scripts did. The tests never saw it because the throwaway PostgreSQL ran them as a true superuser. Now the roles are created with the defaults (already without those attributes), only `LOGIN` and the password are altered, and the attributes are checked afterwards: a pre-existing `smartkin_owner` or `smartkin_app` with superuser, createrole, createdb, replication or bypassrls stops the script with the command to fix it as a superuser. On PostgreSQL 16 and later the creator of a role gets only `ADMIN OPTION`, so the script grants itself `SET` on the owner (needed to hand objects over), and `GRANT CONNECT ON DATABASE`, which needs the database owner, is skipped with a notice when refused. `DatabaseRolesScriptContainerTest` now also runs both scripts as a role with `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS` that is not a superuser (the shape of Supabase's `postgres`), including hand-over of tables that role created and password rotation; its cleanup no longer stops at the first role that does not exist (466 tests).
- `docs/BACKLOG_MVP.md`: the critical path was a plain-text arrow diagram; it is now a Mermaid flowchart, as every diagram in the documentation must be. The rest of the documentation was checked: every other diagram is already Mermaid (the only non-Mermaid fenced blocks left are directory listings in three smartkin-frontend READMEs, not diagrams).
- Child profiles can no longer be taken over by a lost race between two invitations (found by `ChildInvitationContainerTest.aFailedAcceptLeavesTheOtherInvitationUsable`, which failed once on CI with two `201 CREATED` for one user). `ChildEntity` has an id assigned by backbone, so Spring Data could not tell a new row from an existing one and `ChildLinker.create` ended in `merge`: when the first accept had already committed, the second one updated the existing row and moved the child to the second parent instead of failing. `ChildEntity` now implements `Persistable` (new until loaded or persisted), so creating a profile is an insert and a duplicate key answers 409. New deterministic test `linkingAnExistingChildNeverMovesItToAnotherParent`; the concurrent test was repeated six times and the full suite passes (457 tests). `EventEffectsContainerTest` now links the child to the parent instance it saved, which `merge` used to forgive.
- `bootstrap.yml` used the old `prx.*` property names for what the com.umdc libraries bind, so the application context could not start: `AuthProperties.getClients()` was null and `BackboneFeignConfigurer` threw a `NullPointerException`. The settings now live under the names the libraries read: `umdc.security.auth.clients`, `umdc.security.jwt`, `umdc.api.endpoint`, `umdc.backbone.base-url`, `umdc.management.clientRoles` and `umdc.logging.trace.enabled` (the JWT secret and expiration, the backbone and mercury clients and `AUTH_ROLE_ID` take the same environment variables as before). A test binds them from `bootstrap.yml`. Found while smoke-testing the container image (the JV-3 library move did not rename them and no test started the whole context).

### Added
- KF-2: SmartKin consumes its own domain events (`SmartKinEventListener`, group `smartkin-backend`). `ACTIVITY_ASSIGNED` creates an inbox notification for the child;
  `QUIZ_COMPLETED` books the score as points when the quiz was passed; `ACHIEVEMENT_EARNED` books the achievement's points and notifies the child. Points also raise
  `child.total_points`. Effects are idempotent (existence checks plus the unique indexes of migration `V3__idempotent_event_effects.sql`).
  Email requests to mercury keep going through `EmailMessageProducerService` to `prx.producer.mercury.topic`.
- KF-3: consumer retries and error topic. A failing record is retried with exponential back-off (`KAFKA_CONSUMER_MAX_ATTEMPTS` 4 in total, 1s start, x2, 30s cap) and then
  published to `smartkin.events.error.v1` (`KAFKA_ERROR_TOPIC`) with the exception in its headers. Malformed records (JSON or payload errors) skip the retries.
  `KAFKA_CONSUMER_ENABLED=false` turns the listeners off.
