# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Removed
- `PRX_VERIFICATION_CODE_TEMPLATE_ID` / `umdc.verification.code.template.id` (the optional fallback id of the verification e-mail) and its `UMDC_VERIFICATION_CODE_TEMPLATE_ID` line in `config/native.env`. The template id of every e-mail now comes only from mercury (`TemplateIdRegistry`, by file name `sk_<kind>_<language>`). With no `sk_verification_<language>` listed, `MercuryMailer` throws `MailDeliveryException` instead of using a stale configured id. Mercury's own property of that name (the template type id) is unaffected.

### Fixed
- A mercury that could not be reached was invisible in the log: `TemplateIdRegistry` printed only the exception class and the fallback id hid the failure. The warning now carries the exception class and message, and the `MailDeliveryException` of a failed hand-over includes them too (no address, code or token).

### Changed
- **Mail templates are managed like zerobound's.** SmartKin no longer holds template ids in its configuration: `TemplateIdRegistry` asks mercury (`GET /api/v1/messages/template-definitions?applicationId=`) and keeps the answer in memory (refreshed after 5 minutes and, at most every 30 seconds, on a miss), and reads what each template is for from its file name, `sk_<kind>_<language>.ftl` (`sk_verification_es`, `sk_password_reset_en`). A template created, changed or switched off in mercury (or edited from Iris) is seen with no deployment. The language is `umdc.smartkin.mail.language` (`es`). The reference files live in the central `templates/smartkin/` folder (`docs/mercury-templates/` is gone). `PRX_PASSWORD_RESET_TEMPLATE_ID` / `umdc.password-reset.template.id` is **removed** (it never reached a release); `PRX_VERIFICATION_CODE_TEMPLATE_ID` / `umdc.verification.code.template.id` is now **optional**, used only while mercury lists no `sk_verification_<language>`. Mercury must have a template for the application (its caller's own) of each kind, or the e-mail is refused with `MailDeliveryException`.

### Added
- Password recovery ("forgot my password"): `POST /api/v1/password-recovery/forgot` (`{email}`; always `202`, so it never reveals which e-mails are registered; one code per e-mail per minute) and `POST /api/v1/password-recovery/reset` (`{email, code, newPassword}`; `204`, `406` for a wrong, spent or expired code or an unknown or inactive account, `422` when backbone's password policy refuses the password, `502/503` when backbone or mercury fail). Both are public (`@SkipSessionValidation`). SmartKin e-mails a single-use `####-####` code through mercury with its own template (`sk_password_reset_<es|en>.ftl`, kept with the other SmartKin templates in the central `templates/smartkin/` folder; its id is asked to mercury, see "Changed"), mercury keeps it, counts three attempts and expires it, and only a right code reaches backbone's new `lookup-by-email` and `password` endpoints (branch `feat/sak-password-reset-endpoints` of backbone-rest, scope `users:manage`, already SmartKin's M2M scope). A reset never falls back to the "latest status" recovery of the account confirmation. No migration. Needs backbone-rest with those endpoints and the template registered in mercury before it can send mail. See `docs/TECHNICAL_GUIDE.md` and `docs/USER_GUIDE.md`.
- Family contract of the parent: `GET` and `PUT /api/v1/parents/me/family-contract` (operations `getFamilyContract`, `putFamilyContract`, in `docs/api/openapi-v1.yaml`). The contract is a family name, 1 to 30 rules (up to 300 characters each), the parent's typed signature and the agreement date (today when omitted); one per parent, kept in the MongoDB collection `family_contracts` keyed by the parent's user id, so there is nothing to migrate. Only a parent reaches it, and only their own: the key is the `uid` of the token (`403` otherwise; `404` before the first save; `503` when MongoDB fails). It replaces the contract the dashboard kept in the browser's `localStorage`.

### Security
- `GET/PUT/DELETE /api/v1/users/{id}` and the code confirmation (`POST /api/v1/user-register`) did not check whose account it was: any signed-in user who knew a UUID could read, change or delete another account. Now the caller (the `uid` of the session token) must be the user (a parent may also read the account of a child linked to them), otherwise `403` with `message-error`. `PUT` and `DELETE` of `/users/{id}` now take the `session-token` header. `PUT /users/{id}` also refuses `roleIds` (`403`): a user must not choose their own roles. The clean-up of a child account that failed to complete uses the new internal `UserService.deleteUser`, not reachable from an endpoint.
- A session whose e-mail is not verified is kept out of the API. New `VerifiedSessionInterceptor` (registered after the library's session interceptor): without `vcCompleted=true` in the token every operation answers `403` (`message-error: Verify your e-mail to use SmartKin.`) except sign-up, the code confirmation and resend, `/auth/**` and reading the own account. Switch off with `umdc.smartkin.verification.required=false` (accounts that predate the verification).

### Added
- (These two operations are not in `docs/api/openapi-v1.yaml`: that contract does not define `/users` and `/user-register`, and `OpenApiContractTest` enforces it; they are documented in the technical guide.)
- `POST /api/v1/user-register/{userId}/resend`: sends a new verification code (the pending one stops working in mercury). Answers `202`, `403` (not your account), `409` (already verified), `404`/`502` (backbone) or `503` (mercury did not take the message). The e-mail and the name come from backbone, never from the request. The idempotency key is per user and minute, so a double click sends one e-mail.
- `POST /api/v1/profile/image` (multipart, part `imageData`): stores the profile image of the caller in backbone. The BFF already called it; the endpoint did not exist.

### Fixed
- The session token issued to a user whose verification is still pending had no `uid` claim (only the verified branch set it), so the ownership checks could not tell who they were. Both branches now set it; a backbone token without a `uid` is refused with `403`.

### Changed
- **Breaking for operators. SmartKin no longer sends notifications to mercury through Kafka; it uses mercury's HTTP API, like zerobound-rest.** The verification e-mail of a new account is now handed to mercury with `POST /api/v1/messages` (channel `email`, `templateDefinedId`, `userId`, `target`, `language`, `from`, `params` `vc` and `user_name`) using mercury's M2M token (`MercuryTokens`) and `Idempotency-Key: REGISTER-CODE:<userId>`. Mercury answers 202 (`OPENED`) and sends, retries and archives on its own. New `MercuryMailer`, `MercuryMessageRequest`/`MercuryMessageResponse`, `MailDeliveryException` and `MercuryClient.sendMessage`. Removed: `EmailMessageProducerService(Impl)`, `EmailMessageTO`, `Recipient`, the property `umdc.producer.mercury.topic` and the variable `MERCURY_EMAIL_TOPIC` (nothing to configure for it any more). The Kafka domain events (activity assigned, quiz completed, achievement earned) and their consumers are unchanged. If mercury does not take the message, sign-up answers 503 and the just-created backbone user is removed.
- `POST /api/v1/users/confirm-code` (confirm a verification code): when mercury accepts the code (202) SmartKin now activates the user in backbone (`PUT .../users/application/{applicationId}/user/{userId}/activate`, scope `users:manage`) and answers 200. On a mercury 404 (no code left) it reads `latest-status`; if the latest code was verified it activates, so an activation that failed after a right code is recovered by asking again. Mercury's `Attempts-Remaining` header is relayed on a wrong code (406). If backbone cannot activate, the answer is 502.
- Removed the mercury alias/password login (`MERCURY_LOGIN_ALIAS` / `MERCURY_LOGIN_PASSWORD`, `umdc.clients.mercury.login.*`): mercury dropped it in favour of the Backbone M2M token. **Action needed:** the template of the verification e-mail must be registered in mercury (`sk_verification_<language>`, see mercury's `scripts/smartkin/seed-templates.sql`) and `PRX_VERIFICATION_CODE_TEMPLATE_ID` must hold its `template_defined_id`; optional `umdc.smartkin.mail.language` (default `es`) and `umdc.smartkin.mail.from` (default `support@latinhub.info`).

- **Breaking for operators.** SmartKin no longer logs in to mercury with an alias and a password. It asks backbone-rest for the Backbone M2M token of its own managed client (`POST /api/v1/managed-clients/token`, scopes `mercury:message:read` and `mercury:message:write`), sends it as `Authorization: Bearer` to mercury's `POST /api/v1/auth/token` and receives mercury's own M2M token, tied to the SmartKin application, which it sends in `session-token`. New `MercuryTokens` caches both tokens until a minute before they expire and retries once, with fresh tokens, when mercury answers 401. `MercuryAuthClient` and `BackboneManagedClient` are Feign clients without the OAuth interceptor, so the Bearer is not sent twice. `MercuryClient.token` and the `session-token-bkd` header towards mercury are gone. `UserRegisterServiceImpl.confirmCode` no longer reads the user from backbone: it used to send that user's alias **and password** to mercury. **Action needed, in this order:** (1) deploy backbone-rest, `security-oauth` and mercury with the Backbone-token exchange (mercury PR #89); (2) create SmartKin's managed client in Backbone, tied to the SmartKin application, with the scopes `mercury:message:read` and `mercury:message:write`; (3) put `MERCURY_M2M_CLIENT_ID` and `MERCURY_M2M_CLIENT_SECRET` in Vault (optional `MERCURY_M2M_SCOPES`); (4) deploy this. Until then confirming a code and the verification status at sign-in fail. See `docs/TECHNICAL_GUIDE.md` ("Authentication towards mercury") and `docs/USER_GUIDE.md`.

### Fixed
- When mercury refuses smartkin-backend\'s own login client (`401`), login answers `502` with `message-error: Mercury login failed` and the log names the alias that was refused; the code confirmation and the activation answer `502` too instead of relaying a `401`/`403` that would read as an expired session. `BackboneFailure` became `UpstreamFailure`, shared by backbone and mercury.
- Login (`POST /api/v1/auth/session-token`) answered `500`: the mercury Feign interceptor still asked the Keycloak-style token server for a Bearer (`404` on `/auth/realms/umdc/token`), and smartkin presented the **visitor\'s** alias and password to mercury, whose `POST /api/v1/auth/token` is a registry of backend services (`umdc.mercury.login-clients`). New `MercuryServiceLogin` logs smartkin-backend in to mercury as a service with `MERCURY_LOGIN_ALIAS` / `MERCURY_LOGIN_PASSWORD` (falling back to `MERCURY_USERNAME` / `MERCURY_PASSWORD`); `AuthServiceImpl` and `UserRegisterServiceImpl.confirmCode` use it, and `confirmCode` no longer reads the user\'s password from backbone. The mercury interceptor adds no Bearer. Mercury must have that pair in its `login-clients`: today it lists only `DIRECTORY_BACKEND_*` and `ZEROBOUND_*`.
- Nobody activated a user: sign-up creates it inactive and backbone answers `401` to the session of an inactive user, so nobody could sign in after registering. `confirmCode` now calls backbone's `PUT /api/v1/users/application/{app}/user/{id}/activate` once mercury accepted the code (the way zerobound-rest does). Users registered before this change stay inactive: activate or delete them in backbone.
- A missing Kafka topic (`MERCURY_EMAIL_TOPIC`, mercury's `mercury-email-messages`) made sign-up hang 60 s and answer `500` with the user already created in backbone. The producer now waits at most 10 s (`max.block.ms`), and when the verification e-mail cannot be queued the user is removed from backbone and the answer is `503` with `message-error: Verification e-mail could not be sent`. The topic itself must exist in the Kafka cluster: neither smartkin-backend nor mercury creates it.
- In the native image the sign-up answered `500` right after backbone created the user, and mercury never got the verification e-mail: Jackson failed with `UnsupportedFeatureError: Record components not available for record class EmailMessageTO` because records serialized with a hand-held `ObjectMapper` are invisible to Spring AOT. `NativeRuntimeHints` now registers them (`EmailMessageTO`, `Recipient`, `SmartKinEvent` and its payloads, `AchievementRule`, `LessonSummary`, and their enums), which also covers the Kafka events and the Redis lesson cache that fail the same way.
- Sign-up answered `Identity service error` after the e-mail and alias checks passed: backbone answered `400` to `POST /api/v1/users` because `notificationSms`, `notificationEmail` and `privacyDataOutActive` went out as `null` (the sign-up form leaves them optional, and backbone declares them as primitive booleans: "Cannot map null into type boolean", the same note is in zerobound-rest's `BackboneJson`). `UserCreateMapper.toBackbone` now sends `false` when the visitor did not choose.
- `umdc.clients.backbone.url` / `umdc.clients.mercury.url` defaulted to `https://prx-qa.backbone.tst/...`, a host that exists nowhere, and read `BACKBONE_BASE_URL` while the Config Server defines the same property with `BACKBONE_URL` and `https://api.umdc-qa.tst/backbone`. When the remote value did not arrive the calls failed with `prx-qa.backbone.tst` unresolved (Feign status -1). The default is now the nginx URL and `BACKBONE_URL` / `MERCURY_URL` are honoured as well.
- Sign-up answered `409 Email already exists` for brand-new e-mails whenever backbone could not be reached or refused the call (a host that does not resolve, TLS, `401`/`403`): `UserServiceImpl.create` turned every `FeignException` into that conflict. Now only backbone's `409` (its e-mail check answers `409` when the e-mail is taken, `200` when free) is `Email already exists`; a refusal of smartkin-backend's own credential (`401`/`403`) or no answer at all is `502`, and any other status is relayed, with `message-error: Identity service error`.
- The container used the code default `https://prx-qa.backbone.tst/backbone` (and `/mercury`), a name that does not resolve inside it, so every sign-up failed there. `config/local.env` now sets `BACKBONE_BASE_URL` / `MERCURY_BASE_URL` to `https://api.umdc-qa.tst/backbone` and `/mercury` (through nginx, as zerobound-rest documents).
- The Feign calls to backbone and mercury (for example `GET /api/v1/users/check/email/...` during sign-up) failed with `PKIX path building failed`: Feign's default HTTP client trusts only the JVM trust store. `BackendFeignConfigurer` now provides a `feign.Client` that uses the `smartkin-security` SSL bundle (the internal CA), as the token request already did.
- The backbone token is requested with smartkin-backend's own managed client, `BACKBONE_REGISTRATION_CLIENT_ID` / `BACKBONE_REGISTRATION_CLIENT_SECRET` (scope `users:manage`, `BACKBONE_M2M_SCOPES`), as zerobound-rest does; `BACKBONE_CLIENT_*` stay with the security-oauth library.
- Sign-up (`POST /api/v1/users`) answered `500` with `PKIX path building failed` and then `404` on `/auth/realms/umdc/token`. `BackboneFeignConfigurer` now obtains its bearer from backbone's managed-client endpoint (`POST /api/v1/managed-clients/token` with `clientId`, `clientSecret`, `scopes`, answered as `accessToken`), the way zerobound-rest does, instead of a Keycloak-style form post that backbone no longer serves. The request goes through the `smartkin-security` SSL bundle, so it trusts the internal CA (a plain `RestTemplate` uses the JVM trust store). The token is kept until a minute before its `exp`. The client is the registration client (`BACKBONE_REGISTRATION_CLIENT_ID` / `BACKBONE_REGISTRATION_CLIENT_SECRET`, Vault), not `BACKBONE_CLIENT_*`. The M2M scopes come from `BACKBONE_M2M_SCOPES` (default `users:manage`), not from the legacy Keycloak `BACKBONE_SCOPE` (`openid`), and must be registered for the managed client. `MercuryFeignConfigurer` is unchanged (its contract is not confirmed).
- Local start from the IDE failed with `KeyStore not exists: class path resource [file:certs/smartkin/umdc-truststore.jks]`: Vault stores `SSL_JKS_SRMN_TRUSTSTORE_LOCATION` as `file:certs/...` and the Config Server builds `eureka.client.tls.trust-store` as `classpath:${SSL_JKS_SRMN_TRUSTSTORE_LOCATION}`. `config/local.env` now sets the `SSL_JKS_SRMN_*` names (locations, types and the dev password `changeit`) to the jar's own copies.

### Added
